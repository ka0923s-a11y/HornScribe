#11 FND-001: Define canonical IDs, provenance, score revisions, and project schema v1

## Goal

Define HornScribe's durable data contracts before UI and transcription implementations begin to depend on unstable object shapes.

## Why this is first

Score selection, Concert/Horn switching, Verovio hit-testing, review decisions, undo/redo, autosave, and re-quantization all require stable identity and revision semantics.

## Deliverables

### Canonical identity

Define:

- RawNoteEvent ID
- canonical ScoreNote ID
- score revision ID
- source/provenance links
- Concert/Horn view identity rule

Rules:

- Concert and Horn in F refer to the same canonical musical note ID.
- presentation IDs are not domain IDs.
- re-quantization creates a new score revision.
- preserve source RawNoteEvent IDs where mapping is known.

### MusicXML identity

Define deterministic export IDs for `note/@id` and document how canonical note IDs map to MusicXML/Verovio elements.

### Project schema v1

Specify at minimum:

- schemaVersion
- projectId
- source path + content hash
- transcription backend/version/settings
- raw result reference
- canonical score revision
- quantization settings
- user edits
- review decisions
- optional UI session state

### Persistence rules

- atomic write
- recovery snapshot
- migration entry point
- missing-source relink by hash
- cache is rebuildable/non-authoritative

## Acceptance criteria

- [ ] JSON schema or equivalent typed contract exists
- [ ] example project fixture is committed
- [ ] IDs are deterministic within defined revision semantics
- [ ] Concert/Horn share canonical identity
- [ ] MusicXML note IDs map back to canonical notes
- [ ] schemaVersion is required
- [ ] round-trip serialization test exists
- [ ] corrupt/unknown schema version fails safely
- [ ] migration interface exists even if only v1→v1 initially
- [ ] docs explain which data is authoritative vs derived

## Non-goals

- database
- cloud sync
- portable embedded-audio project bundle
- final undo implementation
